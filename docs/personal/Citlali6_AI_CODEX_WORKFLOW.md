# Citlali6 个人 GitHub × ChatGPT × Codex 协作流程

> **适用范围：仅限 GitHub 用户 `Citlali6` 自己发起、授权和交付的 AmazingHand 开发任务。**
> 本文是个人工作偏好记录，**不属于团队强制规范**；不对 `Tom-mr33` 或其他协作者分配任务、规定开发方式、约束工作进度或代替审批。
> 仓库已有 `AGENTS.md`、`docs/GIT_WORKFLOW.md` 及 GitHub 保护规则优先；如有冲突，以团队规则为准。本文不修改这些文件。

## 目的与分工

将个人负责的任务组织成有证据、可迭代的开发闭环：

`Citlali6 确定目标 → ChatGPT 审查现有 GitHub 源码/历史并提出 Issue → Citlali6 授权并启动 Codex → Codex 实现、提交、推送任务分支、创建 PR → ChatGPT 根据远程源码/PR/日志审查 → Citlali6 决定返工、下一轮或提交团队审查`。

- **Citlali6**：确定目标与优先级；批准个人任务的 commit/push/PR、影响硬件的操作及关键方案；负责真实 Z19/FMC/供电/拨码/接线和板端观测；遵守团队 Review/合并流程。
- **ChatGPT**：基于 GitHub 的实际源码、Issue、PR、分支及可核查日志分发个人任务；复查具体提交和验收证据、指出阻断及安排下一轮。不能访问远程时说明限制；不把本地口头汇报当作 GitHub 已交付。
- **Codex**：读取目标 Issue、`AGENTS.md` 和团队流程，保护当前工作区/工作树；在属于本人的独立任务分支实现功能、执行必要验证、根据本人明确授权 commit、push、创建 PR，并提供可复核的代码和结果。
- **其他协作者**：不受本个人文档约束；其仓库分支、PR、任务和工作树不在本人的 Codex 授权范围内。

## 单轮闭环（个人任务）

1. **读取基线**：ChatGPT 检查 `main` 最新提交、相关 Issue/PR、分支和实际进度；把“已实现”“报告通过”“现场未验证”分清。
2. **Issue 发布**：以可运行功能为导向，一项任务尽量形成一条端到端功能链；明确输入、输出、代码位置、必要验收、阻断、现场操作、范围和禁止事项。发布失败必须明确说明，不得虚称已创建。
3. **Codex 开工**：个人主动启动 Codex，指定 Issue URL 和仓库。执行前查看 `git status`、当前分支、worktree、origin、现有 commit；有未提交成果时保护现场，不擅自 stash/reset/清理。新工作从最新 `main` 创建独立分支；已有对应未提交工作时优先在原任务分支安全续作，不强行切换。
4. **优先落地**：先交一个真实可操作的最小链路；只运行与改动有关的必要测试和至少一次端到端验证。避免重复冒烟、无关重构、冗长文档与为了报告而制造大量小任务；急停、安全默认值、失败退出等必要保护不可省略。
5. **远程交付**：经本人明确批准后检查差异、密钥、生成物，再 commit 并 push **当前任务分支**，随后在本人授权范围创建 PR（通常先 Draft）；必须附完整 PR URL、head SHA、验证命令、结果和未完成项。**本地提交、未 push 的分支不算交接完成。**
6. **ChatGPT 审查**：直接阅读远程 PR 的实际 diff、提交、运行日志及证据；必要时在 PR/Issue 留复核意见。明确结论：`可继续联调 / 需修复 / 需要 Citlali6 现场操作`。ChatGPT 审查不等于队友 Approve。
7. **下一轮**：由本人决定是否进入下一轮 Issue，或提交队友 Review。未经团队规则要求的其他队员审批，不将 PR 合并到 `main`；Codex 不自动 merge、不删远程分支。

## 每次 Codex 交付给 ChatGPT 的最小回执

- 对应 Issue URL；PR URL；任务分支；base 和 head SHA；是否已 push。
- 实际交付了什么可运行功能；对应的入口、关键修改文件、启动命令。
- **亲自执行过**的验证、命令及原始结果；未实际执行的测试明确标为未验证。
- 仍未完成的真实硬件/外设条件；需要 Citlali6 现场做的接线、拨码、上电、波形与结果回传事项（集中一张清单）。
- 需要 ChatGPT 审查的风险和建议的下一步，不提前声称上板或真实抓取成功。
